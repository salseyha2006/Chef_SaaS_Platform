## Epic 9: Dish & Recipe Management

*   **US-37: Create & Manage Dish (Recipe)**
    *   **Priority:** Must
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **បង្កើតមុខម្ហូបថ្មី ដោយជ្រើសរើសគ្រឿងផ្សំពីស្តុកមកកំណត់បរិមាណប្រើប្រាស់ជាក់ស្តែង**, ដើម្បី **ឱ្យប្រព័ន្ធអាចគណនាថ្លៃដើមសរុបនៃមុខម្ហូបដោយស្វ័យប្រវត្តិ**។

    *   **Acceptance Criteria:**

        **Scenario 1: បង្កើតមុខម្ហូបជោគជ័យ**
        - **Given** ចុងភៅ នៅទំព័រ "Create Dish" ហើយបំពេញឈ្មោះមុខម្ហូប
        - **When** ចុងភៅ ជ្រើសរើសគ្រឿងផ្សំពីស្តុក (យ៉ាងតិចមួយ) ហើយកំណត់បរិមាណប្រើប្រាស់ជាក់ស្តែងសម្រាប់នីមួយៗ រួចចុច "Save"
        - **Then** មុខម្ហូបថ្មីត្រូវបានបង្កើត ព្រមទាំងគណនាថ្លៃដើមសរុប (Total Cost) ដោយស្វ័យប្រវត្តិដោយផ្អែកលើតម្លៃគ្រឿងផ្សំក្នុងស្តុក

        **Scenario 2: បន្ថែមគ្រឿងផ្សំច្រើនមុខទៅមុខម្ហូបតែមួយ**
        - **Given** ចុងភៅ កំពុងបង្កើតមុខម្ហូប
        - **When** ចុងភៅ ចុច "Add Ingredient" ច្រើនដងដើម្បីបញ្ចូលគ្រឿងផ្សំច្រើនមុខ ព្រមទាំងកំណត់បរិមាណនីមួយៗ
        - **Then** ប្រព័ន្ធបង្ហាញតារាងគ្រឿងផ្សំទាំងអស់ ព្រមទាំងបូកសរុបថ្លៃដើមរាល់ពេលមានការផ្លាស់ប្តូរ (Live Calculation)

        **Scenario 3: មិនបានជ្រើសរើសគ្រឿងផ្សំណាមួយសោះ**
        - **Given** ចុងភៅ កំពុងបំពេញ Form បង្កើតមុខម្ហូប
        - **When** ចុងភៅ ចុច "Save" ដោយមិនទាន់បន្ថែមគ្រឿងផ្សំណាមួយ
        - **Then** ប្រព័ន្ធបង្ហាញ Validation Error ថាត្រូវការគ្រឿងផ្សំយ៉ាងតិចមួយ ហើយមិនអនុញ្ញាតឱ្យ Save

        **Scenario 4: បញ្ចូលបរិមាណប្រើប្រាស់មិនត្រឹមត្រូវ**
        - **Given** ចុងភៅ កំពុងកំណត់បរិមាណប្រើប្រាស់សម្រាប់គ្រឿងផ្សំណាមួយ
        - **When** ចុងភៅ វាយបញ្ចូលលេខ 0 ឬលេខអវិជ្ជមាន
        - **Then** ប្រព័ន្ធបង្ហាញ Validation Error ថាបរិមាណត្រូវធំជាង 0 ហើយមិនអនុញ្ញាតឱ្យ Save

    *   **Technical Notes:**
        - Total Cost = Σ (Quantity Used × Unit Price ដែលបំប្លែងតាម Conversion Rate របស់ Unit, ភ្ជាប់ជាមួយ US-27)
        - Table `dish_ingredients` (Junction Table) ត្រូវរក្សា `dish_id`, `ingredient_id`, `quantity_used`, `unit_id`
        - ការគណនាថ្លៃដើមត្រូវធ្វើនៅ Backend (Source of Truth) មិនមែនទុកឱ្យ Frontend គណនាតែឯង ដើម្បីធានាភាពត្រឹមត្រូវ

*   **US-38: View Dish Details & Cost Breakdown**
    *   **Priority:** Must
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **ចុចមើលព័ត៌មានលម្អិតនៃមុខម្ហូប និងមើលតារាងបំបែកថ្លៃដើមតាមគ្រឿងផ្សំនីមួយៗ**, ដើម្បី **វិភាគដឹងថាគ្រឿងផ្សំណាស៊ីថ្លៃដើមខ្ពស់ជាងគេ និងងាយកែសម្រួលរូបមន្ត**។

    *   **Acceptance Criteria:**

        **Scenario 1: មើលព័ត៌មានលម្អិត និង Cost Breakdown ជោគជ័យ**
        - **Given** ចុងភៅ ចុចលើមុខម្ហូបណាមួយពីបញ្ជី
        - **When** ទំព័រព័ត៌មានលម្អិត Load ចប់
        - **Then** ប្រព័ន្ធបង្ហាញតារាងគ្រឿងផ្សំនីមួយៗ ព្រមទាំងបរិមាណ, តម្លៃឯកតា, ថ្លៃដើមរង (Subtotal), និងថ្លៃដើមសរុប (Total)

        **Scenario 2: មើលភាគរយចំណែកថ្លៃដើមរបស់គ្រឿងផ្សំនីមួយៗ**
        - **Given** ចុងភៅ កំពុងមើល Cost Breakdown
        - **When** ប្រព័ន្ធបង្ហាញតារាង
        - **Then** ជួរនីមួយៗត្រូវបង្ហាញភាគរយ (%) នៃថ្លៃដើមសរុប ដែលគ្រឿងផ្សំនោះកាន់កាប់ ដើម្បីងាយកំណត់គ្រឿងផ្សំដែលថ្លៃខ្ពស់បំផុត

        **Scenario 3: គ្រឿងផ្សំណាមួយត្រូវបាន Archive (ភ្ជាប់ US-35)**
        - **Given** មុខម្ហូបនោះមានប្រើគ្រឿងផ្សំដែលឥឡូវត្រូវបាន Archive
        - **When** ចុងភៅ មើល Cost Breakdown
        - **Then** ប្រព័ន្ធនៅតែបង្ហាញឈ្មោះ/តម្លៃចាស់របស់គ្រឿងផ្សំនោះជាធម្មតា ដោយអាចមាន Badge តូចសម្គាល់ថា "Archived"

    *   **Technical Notes:**
        - Endpoint ទាញយក Dish Detail ត្រូវ Join ជាមួយ `dish_ingredients`, `ចុងភៅ_ingredients`, និង `units` ដើម្បីបង្ហាញព័ត៌មានពេញលេញក្នុង Request តែមួយ
        - ភាគរយត្រូវគណនានៅ Backend ឬ Frontend ក៏បាន ប៉ុន្តែត្រូវផ្អែកលើតម្លៃ Total Cost ដដែលដែលទាញពី Server (មិនគណនាដាច់ដោយឡែក)

*   **US-39: Edit Dish / Recipe**
    *   **Priority:** Must
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **អាចកែប្រែព័ត៌មានមុខម្ហូប និងបន្ថែម/បន្ថយបរិមាណគ្រឿងផ្សំឡើងវិញបាន**, ដើម្បី **ធ្វើបច្ចុប្បន្នភាពរូបមន្តឱ្យត្រូវទៅនឹងរសជាតិថ្មី ឬតម្លៃទីផ្សារ**។

    *   **Acceptance Criteria:**

        **Scenario 1: កែប្រែបរិមាណគ្រឿងផ្សំដែលមានស្រាប់**
        - **Given** ចុងភៅ នៅទំព័រ Edit Dish
        - **When** ចុងភៅ កែបរិមាណប្រើប្រាស់របស់គ្រឿងផ្សំណាមួយ រួចចុច "Save"
        - **Then** ប្រព័ន្ធរក្សាទុកបរិមាណថ្មី ហើយគណនាថ្លៃដើមសរុបឡើងវិញភ្លាមៗ

        **Scenario 2: បន្ថែម ឬដកគ្រឿងផ្សំចេញពីរូបមន្ត**
        - **Given** ចុងភៅ កំពុងកែប្រែមុខម្ហូប
        - **When** ចុងភៅ ចុច "Add Ingredient" ដើម្បីបន្ថែម ឬចុច "Remove" ដើម្បីដកគ្រឿងផ្សំណាមួយចេញ រួចចុច "Save"
        - **Then** បញ្ជីគ្រឿងផ្សំ និងថ្លៃដើមសរុបត្រូវបានធ្វើបច្ចុប្បន្នភាពត្រឹមត្រូវតាមការផ្លាស់ប្តូរ

        **Scenario 3: បោះបង់ការកែប្រែ (Cancel)**
        - **Given** ចុងភៅ កំពុងកែប្រែមុខម្ហូប ហើយបានផ្លាស់ប្តូរទិន្នន័យខ្លះ
        - **When** ចុងភៅ ចុច "Cancel" ដោយមិន Save
        - **Then** ប្រព័ន្ធត្រឡប់ទៅព័ត៌មានដើមវិញ ដោយមិនរក្សាទុកការផ្លាស់ប្តូរណាមួយ

    *   **Technical Notes:**
        - ការកែប្រែ `dish_ingredients` គួរប្រើ Strategy "Replace All" (លុបជួរចាស់ទាំងអស់ រួចបញ្ចូលជួរថ្មី) ក្នុង Transaction តែមួយ ដើម្បីជៀសវាង Sync Logic ស្មុគស្មាញរវាង Add/Update/Delete ដាច់ដោយឡែក
        - ត្រូវប្រើ Optimistic Locking ឬ `updated_at` Check ដើម្បីជៀសវាង Conflict ក្នុងករណី Concurrent Edit

*   **US-40: Duplicate Dish (Clone Recipe)**
    *   **Priority:** Should
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **អាចចម្លង (Duplicate) មុខម្ហូបណាមួយដែលមានស្រាប់**, ដើម្បី **ចំណេញពេលវេលាក្នុងការបង្កើតមុខម្ហូបថ្មីដែលមានរូបមន្តស្រដៀងគ្នា ដោយមិនបាច់រើសគ្រឿងផ្សំឡើងវិញ**។

    *   **Acceptance Criteria:**

        **Scenario 1: Duplicate ជោគជ័យ**
        - **Given** ចុងភៅ កំពុងមើលបញ្ជីមុខម្ហូប
        - **When** ចុងភៅ ចុច "Duplicate" លើមុខម្ហូបណាមួយ
        - **Then** ប្រព័ន្ធបង្កើតមុខម្ហូបថ្មីមួយភ្លាមៗ ដោយចម្លងគ្រឿងផ្សំ, បរិមាណ, និងព័ត៌មានទាំងអស់ដូចដើម ប៉ុន្តែដាក់ឈ្មោះថ្មី (ឧ. "ឈ្មោះដើម (Copy)")

        **Scenario 2: កែប្រែមុខម្ហូបថ្មីដោយឯករាជ្យពីមុខម្ហូបដើម**
        - **Given** មុខម្ហូបថ្មីត្រូវបានបង្កើតដោយ Duplicate រួច
        - **When** ចុងភៅ កែប្រែគ្រឿងផ្សំ ឬតម្លៃរបស់មុខម្ហូបថ្មីនេះ
        - **Then** មុខម្ហូបដើមមិនត្រូវបានប៉ះពាល់ ឬផ្លាស់ប្តូរតាមឡើយ (Independent Copy)

    *   **Technical Notes:**
        - Duplicate ត្រូវបង្កើត Record ថ្មីទាំង `dishes` និង `dish_ingredients` (Deep Copy) មិនមែន Reference ទៅ Record ដើម
        - ឈ្មោះ Default សម្រាប់ Dish ថ្មី គួរបន្ថែម Suffix ស្វ័យប្រវត្តិ (ឧ. "(Copy)") ដើម្បីជៀសវាង Confusion ជាមួយឈ្មោះដើម

*   **US-41: Archive / Delete Dish**
    *   **Priority:** Must
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **អាចលាក់ (Archive) ឬលុបចោលមុខម្ហូបដែលលែងប្រើប្រាស់ចេញពីបញ្ជី**, ដើម្បី **រក្សាសណ្តាប់ធ្នាប់បញ្ជីមុខម្ហូប ដោយមិនប៉ះពាល់ដល់ទិន្នន័យកម្មវិធីចាស់ៗ**។

    *   **Acceptance Criteria:**

        **Scenario 1: Archive មុខម្ហូបជោគជ័យ**
        - **Given** ចុងភៅ ចុច "Archive" លើមុខម្ហូបណាមួយ
        - **When** ចុងភៅ បញ្ជាក់ (Confirm)
        - **Then** មុខម្ហូបនោះលែងបង្ហាញក្នុងបញ្ជីសកម្ម (Active) ប៉ុន្តែទិន្នន័យនៅតែមានក្នុង Database

        **Scenario 2: Restore មុខម្ហូបដែល Archive រួច**
        - **Given** ចុងភៅ មើលបញ្ជីមុខម្ហូបដែល Archived
        - **When** ចុងភៅ ចុច "Restore" លើមុខម្ហូបណាមួយ
        - **Then** មុខម្ហូបនោះត្រឡប់មកបង្ហាញក្នុងបញ្ជីសកម្មវិញ

        **Scenario 3: លុបចោលទាំងស្រុង (Hard Delete)**
        - **Given** ចុងភៅ ចង់លុបមុខម្ហូបចោលជាអចិន្ត្រៃយ៍
        - **When** ចុងភៅ ចុច "Delete Permanently" ហើយបញ្ជាក់ Confirm Dialog
        - **Then** ប្រព័ន្ធលុប Record ចេញពី Database ជាអចិន្ត្រៃយ៍ (មិនអាចទាញត្រឡប់វិញបាន)

    *   **Technical Notes:**
        - Archive ត្រូវជា Soft Delete (`status = archived`) ដូច Pattern ក្នុង US-30/US-35
        - Hard Delete ត្រូវត្រួតពិនិត្យថាមុខម្ហូបនោះមិនត្រូវបានប្រើក្នុង Order/Table Calculation ចាស់ណាមួយ (ភ្ជាប់ជាមួយ `catering-recipe-system`) មុនអនុញ្ញាតឱ្យលុប

*   **US-42: Auto-Update Dish Cost (Dynamic Costing)**
    *   **Priority:** Must
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **ឱ្យប្រព័ន្ធធ្វើបច្ចុប្បន្នភាពថ្លៃដើមមុខម្ហូបដោយស្វ័យប្រវត្តិ នៅពេលខ្ញុំកែប្រែតម្លៃគ្រឿងផ្សំក្នុងស្តុក**, ដើម្បី **មិនបាច់ចំណាយពេលអង្គុយកែប្រែថ្លៃដើមដោយដៃនៅពេលទំនិញឡើងចុះថ្លៃ**។

    *   **Acceptance Criteria:**

        **Scenario 1: ថ្លៃដើមមុខម្ហូបធ្វើបច្ចុប្បន្នភាពស្វ័យប្រវត្តិ**
        - **Given** មុខម្ហូបណាមួយកំពុងប្រើគ្រឿងផ្សំ "សាច់មាន់" ដែលមានតម្លៃចាស់
        - **When** ចុងភៅ កែប្រែតម្លៃ "សាច់មាន់" ក្នុងស្តុក (US-34)
        - **Then** ថ្លៃដើមសរុបរបស់មុខម្ហូបទាំងអស់ដែលប្រើគ្រឿងផ្សំនោះ ត្រូវបានគណនាឡើងវិញស្វ័យប្រវត្តិភ្លាមៗ (ដោយមិនតម្រូវឱ្យ ចុងភៅ ចូលកែម្ហូបម្តងមួយៗ)

        **Scenario 2: មើលឃើញការផ្លាស់ប្តូរថ្លៃភ្លាមៗនៅគ្រប់ទីកន្លែងពាក់ព័ន្ធ**
        - **Given** ថ្លៃដើមមុខម្ហូបទើបផ្លាស់ប្តូរដោយស្វ័យប្រវត្តិ
        - **When** ចុងភៅ មើលបញ្ជីមុខម្ហូប ឬ Cost Breakdown ម្តងទៀត
        - **Then** តម្លៃដែលបង្ហាញត្រូវជាតម្លៃថ្មីតែម្តង (មិនមែនតម្លៃចាស់ Cache)

    *   **Technical Notes:**
        - ថ្លៃដើមមុខម្ហូបមិនគួររក្សាទុកជា Static Value ក្នុង `dishes` Table ឡើយ គួរគណនាជា Real-time (Computed on Read) ដោយ Join ជាមួយតម្លៃបច្ចុប្បន្នរបស់ `ចុងភៅ_ingredients`
        - ប្រសិនបើត្រូវការ Cache ដើម្បីបង្កើនល្បឿន (ឧ. Materialized View) ត្រូវមាន Mechanism Invalidate Cache ភ្លាមៗនៅពេលតម្លៃគ្រឿងផ្សំណាមួយផ្លាស់ប្តូរ (ឧ. Event-driven Recalculation)

*   **US-43: Categorize Dishes (Tags / Menu Types)**
    *   **Priority:** Should
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **អាចបែងចែកមុខម្ហូបជាក្រុមៗ (ឧ. ម្ហូបសម្រន់, ស៊ុប, បង្អែម)**, ដើម្បី **ងាយស្រួលស្វែងរក និងទាញយកទៅរៀបចំជាម៉ឺនុយពេលមានកម្មវិធី**។

    *   **Acceptance Criteria:**

        **Scenario 1: កំណត់ Tag/Category ឱ្យមុខម្ហូបជោគជ័យ**
        - **Given** ចុងភៅ កំពុងបង្កើត ឬកែប្រែមុខម្ហូប
        - **When** ចុងភៅ ជ្រើសរើស Tag/Menu Type មួយ ឬច្រើន (ឧ. "ស៊ុប", "ម្ហូបសំខាន់") រួច Save
        - **Then** មុខម្ហូបនោះត្រូវបានកំណត់ Tag/Category ត្រឹមត្រូវ ហើយបង្ហាញនៅលើ Card/List

        **Scenario 2: Filter បញ្ជីមុខម្ហូបតាម Tag**
        - **Given** មុខម្ហូបជាច្រើនត្រូវបានកំណត់ Tag ខុសៗគ្នា
        - **When** ចុងភៅ ជ្រើសរើស Tag ណាមួយពី Filter
        - **Then** បញ្ជីបង្ហាញតែមុខម្ហូបដែលមាន Tag នោះប៉ុណ្ណោះ

        **Scenario 3: បង្កើត Tag ថ្មីភ្លាមៗ (Inline Create)**
        - **Given** ចុងភៅ កំពុងកំណត់ Tag ឱ្យមុខម្ហូប ហើយ Tag ដែលចង់បានមិនទាន់មាន
        - **When** ចុងភៅ វាយបញ្ចូល Tag ថ្មី ហើយចុច "Create new"
        - **Then** Tag ថ្មីត្រូវបានបង្កើត ហើយកំណត់ភ្ជាប់ជាមួយមុខម្ហូបនោះភ្លាមៗ

    *   **Technical Notes:**
        - ទំនាក់ទំនងរវាង Dish និង Tag ត្រូវជា Many-to-Many (Junction Table `dish_tags`) ដើម្បីអនុញ្ញាតឱ្យមុខម្ហូបមួយមាន Tag ច្រើន
        - Tag ត្រូវផ្គូផ្គងជាមួយ i18n Framework (Epic 1) ប្រសិនបើ Tag ជាទិន្នន័យ System-level (Preset)

*   **US-44: Toggle View (List vs. Grid/Card)**
    *   **Priority:** Should
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **អាចចុចប្តូរទម្រង់មើលបញ្ជីមុខម្ហូបរវាង ទម្រង់បញ្ជី (List) និង ទម្រង់កាត (Card)**, ដើម្បី **ទម្រង់ List ជួយផ្ទៀងផ្ទាត់ថ្លៃដើម ខណៈទម្រង់ Card ជួយងាយស្រួលមើលរូបភាព**។

    *   **Acceptance Criteria:**

        **Scenario 1: ប្តូរពី List ទៅ Card View**
        - **Given** ចុងភៅ កំពុងមើលបញ្ជីមុខម្ហូបជា List View
        - **When** ចុងភៅ ចុចប៊ូតុងប្តូរទៅ "Card/Grid View"
        - **Then** ប្រព័ន្ធបង្ហាញមុខម្ហូបជា Card ដែលមានរូបភាព, ឈ្មោះ, និងថ្លៃដើមសង្ខេប ជំនួសតារាង List

        **Scenario 2: រក្សាទុកជម្រើស View ដែលបានជ្រើសរើសសម្រាប់លើកក្រោយ**
        - **Given** ចុងភៅ ជ្រើសរើស View Mode ណាមួយ (List ឬ Card)
        - **When** ចុងភៅ ចាកចេញ ហើយត្រឡប់មកទំព័រនេះវិញនៅពេលក្រោយ
        - **Then** ប្រព័ន្ធបង្ហាញ View Mode ដដែលដែលបានជ្រើសរើសចុងក្រោយ ដោយមិនត្រឡប់ទៅ Default

    *   **Technical Notes:**
        - View Mode Preference ត្រូវរក្សាទុកក្នុង `localStorage` (Per Device) ឬ ចុងភៅ Setting ក្នុង Database (Sync ឆ្លងកាត់ឧបករណ៍) អាស្រ័យលើតម្រូវការ Consistency
        - Card View ត្រូវការ Field `image_url` សម្រាប់រូបភាពមុខម្ហូប (Optional, បង្ហាញ Placeholder ប្រសិនបើគ្មានរូបភាព)

*   **US-44.1: Create Fixed Dish (ម្ហូបថេរ មិនគិតតាមតុ)**
    *   **Priority:** Should
    *   **Story:** ក្នុងនាមជា **ចុងភៅ**, ខ្ញុំចង់ **អាចកំណត់មុខម្ហូបមួយជា "ម្ហូបថេរ" ដែលគិតថ្លៃដើមតែ ១ ឯកតាក្នុងមួយកម្មវិធី ដោយមិនគុណតាមចំនួនតុ**, ដើម្បី **ឱ្យការគណនាថ្លៃដើមម៉ឺនុយកម្មវិធីត្រឹមត្រូវ សម្រាប់មុខម្ហូបដែលមិនអាចបែងចែកតាមតុបាន (ឧ. នំខេក, ម្ហូបបំពង់មួយទាំងមូល)**។

    *   **Acceptance Criteria:**

        **Scenario 1: កំណត់មុខម្ហូបជាម្ហូបថេរជោគជ័យ**
        - **Given** ចុងភៅ កំពុងបង្កើត ឬកែប្រែមុខម្ហូប
        - **When** ចុងភៅ ជ្រើសរើស "Calculation Type = Fixed (ថេរ)" ជំនួស "Per Table" ហើយបំពេញគ្រឿងផ្សំ និងបរិមាណ រួចចុច "Save"
        - **Then** មុខម្ហូបត្រូវបានរក្សាទុកជាម្ហូបថេរ ហើយបង្ហាញ Badge "Fixed" នៅលើបញ្ជី និង Card

        **Scenario 2: ម្ហូបថេរមិនត្រូវគុណនឹងចំនួនតុ**
        - **Given** ម៉ឺនុយកម្មវិធីមួយមានម្ហូបធម្មតា និងម្ហូបថេរ ហើយចំនួនតុ = 20
        - **When** ប្រព័ន្ធគណនាថ្លៃដើម និងបរិមាណគ្រឿងផ្សំសរុបរបស់កម្មវិធី
        - **Then** ម្ហូបធម្មតាត្រូវគុណនឹង 20 តុ ប៉ុន្តែម្ហូបថេរត្រូវគិតតែ ១ ដងប៉ុណ្ណោះ (ថ្លៃដើមរូបមន្ត × 1) ដោយមិនកើនតាមចំនួនតុ

        **Scenario 3: ថ្លៃដើមម្ហូបថេរមិនប្រែប្រួលតាមចំនួនតុ**
        - **Given** ម៉ឺនុយកម្មវិធីមួយមានម្ហូបថេរមួយមុខ
        - **When** ចុងភៅ ប្តូរចំនួនតុពី 10 ទៅ 50
        - **Then** ថ្លៃដើមរបស់ម្ហូបថេរនោះនៅដដែល ខណៈថ្លៃដើមម្ហូបធម្មតាកើនតាមចំនួនតុ

        **Scenario 4: ប្តូរប្រភេទការគណនារវាង Per Table និង Fixed**
        - **Given** មុខម្ហូបមួយមានស្រាប់ ហើយធ្លាប់ប្រើក្នុងម៉ឺនុយកម្មវិធី
        - **When** ចុងភៅ ប្តូរ Calculation Type
        - **Then** ប្រព័ន្ធបង្ហាញការព្រមាន (Warning) អំពីផលប៉ះពាល់លើការគណនាម៉ឺនុយ ហើយតម្រូវឱ្យបញ្ជាក់ (Confirm) មុន Save

        **Scenario 5: Filter តាមប្រភេទការគណនា**
        - **Given** មានទាំងម្ហូបធម្មតា និងម្ហូបថេរក្នុងបញ្ជី
        - **When** ចុងភៅ ជ្រើសរើស Filter "Fixed" ឬ "Per Table"
        - **Then** បញ្ជីបង្ហាញតែមុខម្ហូបតាមប្រភេទដែលបានជ្រើសរើស

    *   **Technical Notes:**
        - បន្ថែម Field ក្នុង `dishes` Table៖ `calculation_type` (ENUM: `per_table` | `fixed`, Default = `per_table`, NOT NULL)
        - Total Cost (Per Table) = (Σ Quantity Used × Unit Price) × Number of Tables
        - Total Cost (Fixed) = (Σ Quantity Used × Unit Price) × 1
        - ការគណនាត្រូវធ្វើនៅ Backend (Source of Truth) ដូច US-37 ហើយបន្តប្រើ Dynamic Costing តាម US-42
        - Logic ការគណនាម៉ឺនុយកម្មវិធី (`catering-recipe-system`) ត្រូវពិនិត្យ `calculation_type` មុនគុណនឹងចំនួនតុ
        - Record ចាស់ទាំងអស់ត្រូវ Migrate ឱ្យមាន `calculation_type = per_table` ដើម្បីកុំប៉ះពាល់ទិន្នន័យដែលមានស្រាប់
